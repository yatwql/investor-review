# 缓存 TTL 分层收敛 — 现状分析与方案比较

> 文档版本：0.15.6-dev
>
> 定位：`docs/plan/` 中间设计文件（分析结论待评审后实施）。关联任务 `plan-219`。
>
> **一句话问题**：同一个缓存条目的有效期，当前由「代码注册表默认值 + `config.json` 全量副本 + 读侧映射表 + 未注册兜底 + 交易时段特例 + 按 key 抖动」多层合成。层数过多导致「同一条目在不同调用点取到不同值」，已造成两次真实事故（详见 §2）。

---

## 1. 现状：一个缓存条目的 TTL 实际由谁决定

```
调用方（llm/skeleton、cache/cleanup、cache/stats、报告章节…）
   │
   ├─ LLM 侧：get_cache_ttl_llm(模块)        ← 唯一的读侧包装（本轮已瘦身为换名转发）
   │      └─ 模块键 → data_type "llm_<模块>"
   │
   └─ 通用侧：cache.get_ttl(data_type, key=None)
          │
          ├─① 交易时段覆盖：data_type ∈ config.market_hour_aware 且盘中 → market_hour_ttl(30s)
          │        （当前仅 price / index 声明）
          ├─② 用户覆盖：config.cache_ttl[data_type]（若存在，最高优先于默认值）
          ├─③ 代码默认：core/data_registry.DataModuleDef.cache_ttl
          │        （缺省值取自 core/constants 的 CACHE_DAILY / WEEKLY / MONTHLY 常量）
          ├─④ 未注册兜底：CACHE_DAILY + 无告警（历史行为；本轮改为 LLM 侧告警）
          └─⑤ 稳定性修饰：传 key 时叠加 ±15% 确定性抖动（防缓存雪崩），非配置层
```

### 1.1 实际用到的分层数量（按对象类型）

| 对象类型 | 参与层 | 说明 |
|---|---|---|
| 行情类（price/index） | ①+②+③+⑤ | 仅这两类声明了 `market_hour_aware` |
| 其它数据类（news/hold/report…） | ②+③+⑤ | 无交易时段覆盖 |
| LLM 模块（7 个 + 辩论 3 键） | ②+③+⑤ | 不参与 ①；`get_cache_ttl_llm` 只做换名 |

即：**绝大多数条目只有「默认值 + 可选覆盖」两层是真正必要的**，①是行情专属特例，④是安全网，⑤是稳定性修饰——但过去被文档/配置呈现成「四列值」，制造了「很多分类」的错觉。

## 2. 已发生的两起事故（同一根因：同一数值有多份拷贝）

| 事故 | 现象 | 根因 |
|---|---|---|
| A. `self_review` / `holding_change` 反复重算 | 启动清理按注册表 7200s 删文件，读侧按「映射表漏登记 → 回落到 `llm_global_macro`」的 86400s 仍认为有效 → 2h 后刚写的缓存消失，日志只写「无此缓存文件」 | **读侧映射表**与注册表各存一份「模块→TTL」 |
| B. 改默认值后用户无感 | 本次把三个模块改成 4h 后，`config.json` 里仍是 7200/86400 → 运行时仍走旧值，因为 **config 里抄了一份默认值**，无法区分「用户明确改过」与「模板陈旧」 | **配置文件复制注册表默认值** |
| C. 清理可能早于读侧过期（潜在，未报障） | 读侧多数调用点传 `key` → TTL 乘 ±15% 确定性抖动（`holdings_tracker` / `fund` / `index` / `price` / `sentiment` / `fund_purchase` / `fund_fee` 等）；而 `cache/_cleanup.py` 调 `get_ttl(data_type)` **不传 key** → 按 1.0×TTL 判定过期。**抖动因子 >1 的那一半 key，清理会在读侧仍认为有效时（最多早 15% TTL）删掉文件**；反之因子 <1 时只是多留废物。TTL 越长损失越大（4h → 最多 36 分钟） | **同一 key 的有效期由两套算法各自计算** |

**抖动缺陷的量化**：`_ttl_jitter_factor` 在 `[0.85, 1.15]` 上按 301 档取值，清理侧恒取 1.0 → 约**一半**的 key 存在「清理早于读侧过期」的时间窗，最大 15%×TTL。抖动本身是确定性函数（只依赖 key 字符串），清理侧完全可以用同一个 `fkey` 算出同一因子——这是**两个调用点没对齐**，不是设计分歧。

配套证据（本轮实测）：

- `config.json` 的 `cache_ttl` 有 **38** 个键，注册表 **37** 个，其中 `fund_overlap` 是**早已不存在的键**（历史残留，无人读取）。`config/_validation_scalars.py::_validate_cache_ttl` 只校验「值是否正数」，**不校验键是否已注册** → 这类残留键永远不会被告警，也不会被清理。
- 契约测试 `src/test/unit/llm/test_llm_cache_ttl_single_source.py` 用于兜住这类「多份拷贝」的漂移；其存在本身说明护栏成本已产生——属**为架构缺陷附加的护栏**，而非架构本身合理。

## 3. 各层必要性判定

| 层 | 作用 | 是否必要 | 结论 |
|---|---|---|---|
| ③ 注册表默认值 | 代码侧的单一真值（含清理/统计同源） | **必要** | 保留，作为唯一默认来源 |
| ② `config.json` 全量副本 | 用户覆盖 | **必要（但要改形态）** | 保留**稀疏覆盖**能力，模板只写空对象 |
| ① 交易时段短 TTL | 盘中行情必须 30s 级新鲜度 | **必要（局部）** | 保留，明确限定 `market_hour_aware`（当前 price/index） |
| ④ 未注册兜底 | 防止 `KeyError` | **必要（安全网）** | 保留，但必须**可见**（告警），不能静默 |
| ⑤ per-key 抖动 | 防雪崩 | **必要（稳定性）** | 保留，但**读写两侧必须用同一 key 算同一因子**（现状仅读侧应用 → 事故 C） |
| 读侧映射表 + 回退默认字典 | 把模块名翻成 data_type | **不必要** | 已删除（改为 `llm_<模块>` 换名 + 直读注册表） |
| 配置文件里的默认值副本 | 让用户看见默认值 | **不必要** | 建议删除（改为文档呈现默认值表） |

## 4. 方案比较

### 方案 A：维持四层（现状）

- 优点：零改动。
- 缺点：默认值有 2 份持久副本（注册表、config.json），漂移面恒存在；每次改默认值都要「改代码 + 迁移已有 config + 改文档 + 改测试四处」；用户在 config 里删掉键才能回到默认，但无法判断自己改过什么。

### 方案 B：取消 config 覆盖，TTL 只读注册表

- 优点：真值唯一。
- 缺点：丢失用户调优能力（如把 expert_review 从 4h 调到 12h 只能改代码）。与「高级用户可调」的既有承诺冲突。

### 方案 C（推荐）：注册表是唯一默认 + config 稀疏覆盖

1. 生成的 `config.json` 中 `cache_ttl` 写为**空对象**并附注释（默认值见注册表/文档，仅在需要覆盖时添加键）。
2. `get_ttl` 逻辑保持不变：`config.cache_ttl[type]` 存在则覆盖，否则注册表默认，未注册 → `CACHE_DAILY` + 告警。
3. 默认值表只在文档呈现（从注册表生成的静态表，注明「默认值，非配置」）。
4. 已存在用户的 `config.json` 中残留的全量 `cache_ttl` 块**继续作为覆盖生效**（行为不变）；文档给出「想回到默认就删掉该键」的操作口径。
5. 迁移可选：提供一次性「清理等于默认值的 config 键」脚本（仅打印建议，不自动删，避免误删用户显式设定）。

### 4.1 方案 C 必须同时决定的三个次级口径

| 编号 | 问题 | 建议 | 理由 |
|---|---|---|---|
| D1 | 抖动只在一侧应用（事故 C） | 清理侧改为 `get_ttl(data_type, fkey)`——用文件名（即缓存 key）算同一因子；或两侧统一不抖动 | 抖动是确定性函数，两侧同 key 必得同值，天然对齐；删掉抖动会失去防雪崩能力 |
| D2 | `cache_ttl` 里未注册的键永不告警 | 校验时对「不在注册表也不在已知别名表」的键打 WARNING（不自动删） | 让历史残留（如 `fund_overlap`）可见，用户可自行清理 |
| D3 | 过期边界 | 清理判定加一个很小宽限（如 +1% 或 +60s） | 抵消读写两侧的时钟/序列化毫秒差；避免「刚好边界」抖动 |

**为什么 C 能同时解决 A/B 两类事故**：
- 事故 A 属于「同一条目两套读取路径」→ 已由「读侧只换名、直读注册表」消除，测试 `test_llm_cache_ttl_single_source` 仅保留为回归护栏。
- 事故 B 属于「默认值被复制」→ C 让默认值只存在于注册表，config 里出现的键天然意味着「用户显式覆盖」，改默认值时不会再有陈旧副本与之竞争。

## 5. 实施步骤与影响面（待评审后执行）

| 步骤 | 改动 | 影响 |
|---|---|---|
| 1 | `config/_config_defaults.py`：`"cache_ttl": {}`，模板加注释行 | 新装/重置配置的 TTL 段为空白覆盖位（默认值仍由注册表提供） |
| 2 | `how-to-config.md`：`cache_ttl` 章节改为「默认值表（只读，来自注册表）+ 覆盖写法示例」 | 用户视角更清晰 |
| 3 | `technical.md` / `llm-technical.md`：TTL 说明改为「默认 + 稀疏覆盖」两层模型 | 消除「四列值」表述 |
| 4 | 测试：`test_config_consistency` 中「cache_ttl 键集与类型」断言改为「稀疏覆盖语义」；`test_llm_cache_ttl_single_source` 增加「模板不复制默认值」断言 | 契约随架构更新 |
| 5 | `cache/_cleanup.py`：过期判定改用 `get_ttl(data_type, fkey)`（与读侧同一抖动因子）+ 极小宽限 | 消除事故 C 的早删窗口 |
| 6 | `config/_validation_scalars.py::_validate_cache_ttl`：未注册键 WARNING | 历史残留键可见 |
| 7 | 文档：本文件的决策结论并入 `technical.md` 缓存章节，本文归档 | — |

**风险**：
- 依赖「配置里有默认值」的用户操作习惯（在 config 里翻看 TTL）会受影响 → 文档给完整默认值表兜底。
- `config_consistency` 测试对模板键集有断言，需同步改；`check-doc-drift` 的「默认值」校验会校验文档表与注册表一致 → 需保证文档表由注册表派生核对。

**不做**：不改注册表结构、不改 `get_ttl` 的优先级顺序、不动 jitter 与交易时段特例、不自动删除用户 config 中的既有键。

## 6. 验收标准

1. 生成的 `config.json` 中 `cache_ttl` 为空对象（新装/重置场景），且 `get_ttl` 对全部 37 个注册类型返回与注册表一致的值；
2. 用户在 config 中显式写 `cache_ttl.llm_expert_review = 21600` → 该模块读侧/清理侧均取 21600（覆盖生效）；
3. 删除该键 → 回到注册表默认值（4h）；
4. 未注册类型 → `CACHE_DAILY` + WARNING（不得静默借用其它类型）；
5. 对同一缓存文件名，读侧（`cache.get` 传入的 TTL）与清理侧（`cleanup_expired` 判定）**取值逐字节相等**（新增契约测试，覆盖抖动因子 >1 与 <1 两侧）；
6. `cache_ttl` 中未注册键在校验时产生 WARNING（`fund_overlap` 类残留可见）；
7. `test_llm_cache_ttl_single_source` 全绿；`check-doc-drift` 默认值表校验通过。
