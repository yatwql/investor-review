## 2. 现状地图

主循环只有一条：`src/python/tui/tui.py::main()` —— 渲染整帧（页眉 + 状态行 + 分组菜单 + 页脚），内层逐键循环；方向键在 POSIX + TTY 下原地重绘（`_clear_last_frame` 上移清屏），其余环境整屏追加。二级界面走 `panel_runtime.panel_loop` + `NavState`（游标 / engaged 两态），`?` 与 `0` 由运行时统一承接。

交互能力的分布如下，右侧一列即本次探讨的空档：

| 能力 | 现状落点 | 空档 |
|:--|:--|:--|
| 入口发现 | 分 5 组的主菜单 + 字母/数字直达 + 首页 `/` 子串筛选 | `/` 只在首页；面板内 18 项级别的列表无筛选 |
| 导航 | 全档 ↑↓ + Enter；窄档另保字母直达 | 无 `j/k` 等等价键、无「跳到首/末项」 |
| 单项说明 | `?` / `?键`（`panel_runtime`）| 首页没有 `?`（键位速查只在手册里） |
| 长任务 | `report/progress.py::TuiProgressReporter` 逐行 `[..]/[OK]`；`stage_progress` 给「阶段 · 已耗时 · 预计剩余」 | 进度是**追加行**，滚上去就丢；跑到一半想中止只能关程序（Ctrl+C 直接退出） |
| 长输出 | 5 处「按任意键」闸门（日志 200 条 / 健康历史 10 条 / 自检 / 缓存摘要 / 远程产物清单） | 无分页、无翻页、无检索；窄屏大字块会在读完前滚出可视区，闸门只是在补偿 |
| 错误反馈 | `[ERR] 原因`，部分站点带「详见日志」 | 契约要求「原因 + 下一步动作」，仍有站点只给原因（例：`handlers_log._cmd_view_health_history` 的读取失败、`_cmd_run_doctor` 的执行失败） |
| 未知键 | 窄档单行提示；宽/中档 `break` 走整屏重绘 | 宽屏按错键会闪一次整屏重绘，与窄档手感不一致 |
| 配置写入 | `[S]`/`[G]`/`[C]` 每次切换即落盘（经 `handlers_config._apply_edit`） | 没有会话级撤销；想「先试试」只能记住原值手改回 |
| 页头 | `print_header()` 每帧重算首用指引（`os.path.exists` + `llm_status`）；状态行 TTL 记忆 | 首用指引长期占首屏；状态行失效口径散在调用点，未成文 |
| 环境适配 | `core/ansi_colors.py` 按 `NO_COLOR` / 非 TTY 关色 | 符号（`⚗ ▸ █ ─ ├`）与原地重绘没有独立开关，屏幕阅读器 / 纯文本终端无路可走 |
| 会话连续性 | 只记「上次报告时间」（状态行） | 游标、筛选词、刚用过的面板都要每次重找 |

## 3. 议题与方案

每项给出：**现状证据 → 方案选项 → 推荐与理由 → 成本面**。成本面只记「要动哪几类东西」，不展开实施步骤。

### 3.1 长任务的可观测与可中止（议题价值最高）

**现状**：`TuiProgressReporter.info/ok` 都是 `print`，报告生成按模块串行打印，屏上形成一条越来越长的流水；`stage_progress` 有 ETA 但同样按行追加。中止只能靠 Ctrl+C，而 Ctrl+C 在 `tui.py` 顶层被解释为「退出程序」——报告写了一半、会话统计与退出流程一起走。

**方案 A（轻量）**：只在末尾补一句「本阶段耗时排行」（现状已有 `print_timing_summary`），不做过程改进。→ 不解决「跑到哪了」的问题，排除。

**方案 B（推荐）**：**底部状态条 + 协作式取消**。

- 状态条：单行，`\r` 覆写 + 行尾清残，内容复用 `status_line` 的拼装风格（`[..] 阶段名 │ 已 12s │ 约剩 40s │ q 中止`）。非 TTY / 无 ANSI 直接退回逐行追加，管道行为不变。
- 进度载体：`ProgressReporter` 加一个 `snapshot()`（阶段、已完成/总数、已耗时、ETA），TUI 侧做成状态条渲染器；Web / CLI 通道复用同一 snapshot，避免三渠道各写一份。
- 取消：在阶段边界检查取消令牌（协作式，不硬切线程）；已完成的产物与缓存保留，收尾给 `[!] 已中止（完成 3/7 项，缓存已保留）→ 重跑只补缺失`，并**照常**打印耗时排行。

**推荐 B**。理由：这一项同时补掉「看不见进度」「停不下来」「中止后不敢重跑」三个痛点，且不新增任何击键——取消靠状态条上的 `q`，主路径击键数不变，击键基线不受影响。

**成本面**：`report/progress.py`（接口加 snapshot + 取消令牌）、报告生成编排（阶段边界检查）、`tui.py`（状态条生命周期：进入/退出时归还终端状态）、新增用例（取消后产物与文案、非 TTY 降级、状态条行宽与窄档折行）。契约文档：`DESIGN-TUI.md` Feedback 表补长任务状态条一节。

**风险**：`\r` 覆写在 SSH + tmux、手机终端下表现不一（换行算行、宽度探测滞后）。缓解：只在「本轮输出全部由状态条产生」的窗口内使用覆写，任何 `[OK]/[!]/[ERR]` 落地行都先清状态条再打；探测到异常（宽度抖动 / 非 TTY）立即退回追加模式。

### 3.2 长输出：分页查看器取代闸门

**现状**：日志视图一次最多 200 条、健康历史 10 条、自检结果逐项 + 建议，全部「一次打满 + 按任意键」。闸门白名单固定 5 处，由 `test_prompt_contract.py::TestPressAnyKeyGateWhitelist` 锁死——这说明闸门位置是稀缺资源，不是常规手段。

**方案 A**：维持闸门，只在窄档做「每条压一行」的压缩（日志与健康历史已部分如此）。→ 压缩到极限仍是「一屏放不下」的问题。

**方案 B（推荐）**：抽一个 **行分页器** `pager.view(title, lines)`：`空格`/`↓` 下翻一屏，`b`/`↑` 上翻，`/` 关键字高亮跳转，`q` 退出；终端行数不足一屏时**直接全打**（保持当前手感、不加击键）。三处闸门（日志 / 健康历史 / 自检）迁到分页器，「按任意键」白名单相应缩到 2 处（缓存摘要 / 远程产物清单）。

**推荐 B**。理由：把「补偿措施」换成「真能力」；顺带减少白名单条目，契约更干净。日志侧还可加「级别 + 关键字」两层过滤（当前只有级别）。

**成本面**：新增 `src/python/tui/pager.py`（约 120 行，走 `text_layout` 折行与 `display_width`）、三个 handler 的渲染段替换、白名单用例更新、新增用例（分页键位矩阵、不足一屏直打、非 TTY 全量打印、窄档折行）。

**风险**：分页器自成一套按键语义（`q` / 空格 / `b`），与面板 `0/B 返回` 有重叠认知。缓解：分页器页脚常驻一行键位提示，且 `q`/`Esc`/`0` 三个都退。

### 3.3 错误尾巴：把「下一步动作」做成单源

**现状**：契约写「`[ERR]` 原因 + 下一步动作」，实际有站点只给原因（例：`[ERR] 读取数据源健康历史失败`、`[ERR] 系统自检执行失败（详见日志）`）；「详见日志」本身也不是可执行路径——用户要到菜单里自己找 `[D]→L`。

**方案**：新增一个极小的 `next_step.py`：错误码 / 错误类别 → 动作短语（`→ [D]→L 看运行日志`、`→ [G]→L 配置 LLM`、`→ [2] 更新行情缓存`）。`TuiProgressReporter.error()` 与各 handler 的 `[ERR]` 站点统一取短语；同时把状态行已用的 `ACTION_TEMPLATES` 与它合并成一份「动作短语表」，避免两处各写。机检沿用状态行那套「首键必须是主菜单顶层键」的子集断言。

**成本面**：新模块（约 60 行）、约 15 处 `[ERR]` 站点改文案、`test_prompt_contract.py` 扩一条「错误行必须含 `→`」的机检、手册配图/文案不变。

**价值判断**：纯文案工程，零交互风险，直接抬用户自救率。**建议在任何一批改进里顺带做**。

### 3.4 未知键反馈：全档统一为单行

**现状**：`tui.py` 内层循环里，窄档未识别键给一行 `「X」未登记（键位见上方菜单）`；宽/中档直接 `break`，靠整帧重绘当反馈——一次按错的视觉代价是一整屏闪动，且会让首用指引重新刷一遍。

**方案**：全档统一走 hint 行（复用现成的 `_print_hint` + `hint_lines` 清帧口径），未登记键一律只出一行提示（帧保持不动），仅当「未知键连续 N 次」时补一句 `?` 看键位。

**成本面**：`tui.py` 内层循环 10 行左右；用例目前按档位分别断言，需改为同语义断言（窄档已有，宽档补齐）。

**风险**：宽屏下 hint 行会短暂压住页脚一行。缓解：hint 行放在帧下方，与现有 `已清除筛选` 等提示同一位置，用户视觉位置不变。

### 3.5 配置面板的「可试可退」

**现状**：`[S]` 每次切换即写盘；`[C]`/`[G]` 同理。想比较两组配置的差异，只能记住原值逐项改回，且面板有 18 项级别的列表。

**方案 A（推荐，轻量）**：**会话内快照 + 一键还原**。进入面板时拍一份配置快照（内存字典），页脚标注 `u 撤销上次 · U 还原进入时`；不改变「切换即写盘」语义，因此不影响任何现有测试与击键基线。退出时若与进入时快照不同，页脚保持一行 `本次改动 3 项（U 可全部还原）`——只报事实，不追问。

**方案 B（重）**：草稿态（改动不落盘，退出时问「保存 / 放弃 / 继续编辑」）。→ 多一次按键，且与 `[S]` 的「实时生效」体验冲突（功能开关要立刻影响首页菜单裁剪），击键基线会被拉长。**不建议**。

**推荐 A**。真需求是「别让我记原值」，不是「别立刻生效」。

**成本面**：`switch_panel` / `handlers_config`（快照与还原路径）、页脚文案（走 `panel_prompt` / `legend_lines`）、新增用例（撤销粒度、还原后磁盘文件与内存一致、功能开关还原后菜单立即复原）。

### 3.6 首页 `?` 速查 + `/` 筛选通用化

**现状**：`?` 只在面板里有；首页有 `/` 子串筛选（`match_menu_items`）但面板里没有。用户在两处的「找东西」方式不统一。

**方案（推荐）**：两步走，第一步便宜。

1. **首页 `?`**：一屏键位速查——分组、直达键、`/` 筛选、`↑↓`/Enter、`Esc` 双击退出、`q`？不引入新键，只把已存在的能力上屏。成本：`tui.py` 加一个分支 + 复用 `panel_runtime` 的帮助渲染；击键基线不变（`?` 不在主路径上）。
2. **`/` 通用化**：把 `match_menu_items` 泛化为「对当前屏的 `PanelItem` 列表做子串/键名匹配」，`[S]`（18 项）、`[C]`（章节）、`[G]`（二级）面板都可用。成本：`panel_runtime.panel_loop` 接入筛选态（游标落入匹配集，与首页已有 `next_matching` 同源）+ 面板页脚一行提示。

**风险**：面板一旦有筛选态，「`/` + 输入」与「直达键」的优先级要定死（建议：筛选态下直达键仍生效，但只对匹配项，未匹配时给一行提示——与首页现有口径完全一致，不新增规则）。

### 3.7 导航键位的低成本扩展

**现状**：只有 ↑↓ + Enter。`j/k`、`g/G`、`Tab` 在 TUI 用户肌肉记忆里是免费的。

**方案**：`j/k` 等价 ↓↑；`g`/`G` 跳首/末（筛选态下跳匹配集首末）；`Tab`/`Shift+Tab` 在分组间跳（主菜单）。这些键当前**均未**被菜单或面板占用（菜单热键是 `E/B/L/W/Q/1/2/3/C/S/G/U/R/D/X`——注意 `g` 与 `G`（全局设置）冲突，需避开：`g` 可考虑让位给 `gg`/`Home` 或干脆只做 `j/k`）。

**建议**：只做 `j/k`（无冲突、零认知成本），`g/G` 因与 `[G]` 全局设置冲突**放弃**。这是一条「试了就知道」的小改动，也可作为分页器（§3.2）键位的复用底座。

### 3.8 页头瘦身

**现状**：`print_header()` 每帧计算首用指引（`os.path.exists` + `llm_status`），缺失持仓或未配 LLM 时首屏固定多出 2~4 行「首次使用指引」，且每次原地重绘都重算一遍。

**方案**：

- **首用指引折叠为一行**：`📋 未就绪：持仓文件 · LLM（[G] 配置）`，详细引导收进 `?`（与 §3.6 合并）；就绪后整块消失。
- **计算移出渲染**：指引状态随配置刷新 / `[R]` 失效（复用状态行已有的 `reset_status_memo` 失效点），不每帧重算。
- **状态行失效口径成文**：把「哪些事件让状态行失效」（配置刷新、报告完成、缓存更新、健康检查完成）写进契约，避免将来新增取数源时各写各的失效点。

**成本面**：`tui_menu.print_header` + `tui/status_line.py` 失效钩子、契约 Feedback 表补一行、用例（未就绪 / 就绪两态 + 首屏行数上限）。

### 3.9 环境适配：符号与渲染模式的独立开关

**现状**：`NO_COLOR` / 非 TTY 只关颜色；符号（`▸ ⚗ █ ─ ├`）与原地重绘仍照用。屏幕阅读器、老旧控制台、日志抓取场景没有退路。

**方案**：两个环境变量（默认关闭，零行为变化）：

- `TUI_ASCII=1`：符号表降级为 ASCII（`>`、`*`、`#`、`-`、`+`、`|`），集中在 `text_layout` 一个符号表里替换，不散落。
- `TUI_PLAIN=1`：禁用原地重绘，走「整屏追加」路径（等价当前非 TTY 分支）。

**理由**：这两条都是「已经存在两条路径，只是没暴露开关」，改动面小、风险低，且让 CI/管道/截图/朗读三场景都稳。

**成本面**：符号表集中（`text_layout` + `switch_panel`）、`_can_repaint_inplace` 增加环境判据、用例（两开关的渲染快照）。

### 3.10 会话连续性（低优先，可延后）

**现状**：每次启动都从配置的 `default_menu_key` 起，筛选词与游标不保留。

**方案**：`data/cache/tui_session.json`（或配置目录）记 `cursor_key` / `filter` / `last_panel`，启动时还原并给一行 `（已恢复上次位置 · 0 清除）`。放在缓存目录、可随时删。

**判断**：收益偏小（用户对「从哪儿开始」不敏感），但成本也小。放在最后，取决于 §3.1~§3.4 之后的余量。

| 3.8 页头瘦身 | 中 | 小 | 无 | Feedback 补一行 | 第三批 |
| 3.10 会话连续性 | 低 | 小 | 无 | 无 | 视余量 |

一个可用的判断口径：**第一批全是「不改交互契约、不改击键数、不动主路径」的改动**，风险最低、见效最快；第二批引入新按键语义（分页器、筛选态、ASCII 开关），需要契约同步；第三批动写路径与页头结构，需要更谨慎的用例铺底。

---

## 5. 明确不做（含理由）

| 候选 | 结论 | 理由 |
|:--|:--|:--|
| 迁到 curses / textual | 不做 | 现有交互契约（提示三段式、行型四类、闸门白名单、反馈前缀）与 17 个 `unit/ui` 用例全部建立在 print 流之上；真全屏带来窗口/滚动/鼠标，代价是整条渲染链路重写，而主场景是手机 SSH——全屏在窄屏与低带宽链路收益反而为负 |
| 主菜单全量重编号为 `1..N` | 不做 | 契约 Known Gaps 已记「已评估未采纳」：键位在三渠道文档 + 用户肌肉记忆里稳定，全量重编号要改约 200 处文档键位并放宽菜单块机检 |
| 数字键语义修正（让 `1..9` 表示「第 N 项」） | 不做，但**上屏说明** | `1/2/3` 当前是缓存操作，与「编号为主入口」哲学存在张力；改键的收益（少数人的直觉）低于回归面（文档 + 基线 + 记忆）。折中：首页 `?` 与页脚明确写「数字键为缓存操作，非序号」 |
| 主菜单按「最近使用」重排 | 不做 | 位置稳定的价值高于命中率；状态行已经承担「上次报告」的时间线索 |
| 鼠标支持 | 不做 | 手机 SSH 无鼠标语义；引入后还要处理坐标 → 项的映射与折行偏移 |
| 进度条动画 / 每 100ms 刷新 | 不做 | 重绘频率换不来信息量（阶段切换才是信息），且低带宽链路会被刷屏；状态条只在**阶段变化**与**每 5s 心跳**时更新 |

## 6. 待确认的决策点

1. **§3.1 取消语义**：中止后是否允许「续跑」（跳过已完成章节，只补缺失）？还是只保证「缓存保留 + 给建议」？（前者要动编排，后者只动 UI）
2. **§3.2 分页器**是否也承载报告产物的 HTML/文本预览，还是只做纯文本行？
3. **§3.5 撤销粒度**：只还原「本次进入面板后的改动」，还是保留最近 N 次跨面板撤销栈？
4. **§3.9 ASCII 档**是否需要作为 `--plain` 启动参数暴露（供 `investor-review --tui --plain` 直接接入脚本），还是仅环境变量足够？

1. 中止语义：**只保缓存 + 给建议**（不做续跑编排），中止后提示「重跑只补缺失」。

## 8. 一句话结论

现有 TUI 的**入口层**（分组菜单、状态行、`?`、`/`、原地重绘）已经相当完整，真正的空档在**过程层**：长任务看不见进度也停不下来、长输出只能靠闸门停屏、错误只给原因不给下一步。因此建议把改进重心放在「过程可见性 + 可中止 + 反馈闭环」，而不是继续对主菜单做结构调整。
