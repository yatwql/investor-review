# TUI 交互人机工程（HCI）治理设计

> **关联**：`docs/managements/plan.md` → **plan-156 ~ plan-165**；触发条目 rf-732（用户反馈「`[L]` 生成提示像要记密码」）。
> **证据底座**：rf-719 ~ rf-732 共 14 条交互修补与 changelog 0.13.7 段——它们不是 14 个独立缺陷，而是同一个设计缺口的 14 次显影。
> **目的**：把「屏幕文案 ↔ 按键语义」从 13 个面板各自手写，收敛为**可机检的交互契约**；与 Web/HTML 侧的 `DESIGN.md`（设计语言契约，含契约结构测试）形成对称。
> **状态**：待评审；本文件不含代码改动。

## 1. 动因：十四个缺陷的同一根因

### 1.1 症状归类

| 缺陷（changelog 可溯） | 表面症状 | 归类 |
|---|---|---|
| rf-732 `[L]` 提示「回车=生成 / f=强制刷新 / q=中止」 | 用户读不出两者差别，还要猜「想选模块该按什么」 | 文案不承载语义 |
| rf-728 三连问合并为单屏 | 以「问数 3→1」为优化目标，牺牲语义密度 | 指标替代了人因目标 |
| rf-721 `[S]` 面板「? 编号 看说明」占位符写法 | 提示语无示例，用户不知道要输入什么 | 文案不承载语义 |
| rf-722 提示语「占位符、看不懂」 | 同上 | 文案不承载语义 |
| rf-717 类：同键不同提示处行为不一致 | 读键/取消语义各处不同 | 一致性缺失 |
| rf-729 方向键误判为孤 Esc | 按了方向键程序却退出 | 评估鸿沟（反馈与操作不符） |
| rf-730 上下键仅首页生效、`[S]` 游标「像没反应」 | 按键无可见结果 | 评估鸿沟 |
| rf-725/726/723 拆包误判、末字节泄漏 | 一次按键触发另一个功能 | 反馈不可解释 |

### 1.2 一句话根因

**屏幕上的字不是一等公民**：语义真值活在代码注释与技术文档里，屏幕上只输出键位暗号。

对照证据：同一件事，代码注释写「回车=默认生成（走缓存）」，屏幕只印「回车=生成」。用户拿到的信息量 = 键位数量，而不是「这个键会发生什么、代价是什么、之后还能不能反悔」。

### 1.3 为什么之前修不完

每轮修复都在**个案**层面收尾（改一句文案、补一个重绘），没有留下判据。于是下一轮新增面板时，同样的缺口重新长出来——`panel_runtime` 收敛了**控制流**（导航态、派发、重绘），但**文案层**仍由各面板手写 `prompt=` 字符串，语义继续漂移。

## 2. 现状体检：HCI 原则对照

| 原则 | 本项目现状（证据） | 判定 |
|---|---|---|
| **识别优于回忆**（Nielsen #6） | 主菜单 19 项全为**英文首字母**（E/B/L/W/Q/P/I/A/S/M/R/V/H/T/X + 1/2/4），标签是中文——中文用户拿不到助记线索 | ✗ |
| **帮助在屏幕内**（#10） | `?` 项说明**仅一个面板实现**（`handlers_config.py:453` 的 `?编号`）；其余面板零帮助 | ✗ |
| **一致性**（#4） | 同一动作四套表达（见 2.2） | ✗✗ |
| **系统状态可见**（#1） | `press_any_key()` **28 处**：每个动作后强制「按任意键」才回菜单 | ✗ |
| **错误预防**（#5） | 主菜单 Esc 连按两次确认（`tui.py:176` `_ESC_EXIT_CONFIRM_WINDOW`）——其根因（读键层用户态缓冲）已由 rf-729 修复，确认层成为遗留摩擦 | △ |
| **符合用户语言**（#2） | 上屏词：强刷 / 走缓存 / 降级 / 分档 / 游标 / 漂移——工程内部词直接给用户 | ✗ |
| **灵活高效**（#7） | 直达字母、键名、词级组合（`f h`）——专家快路已具备，**这块是优点，改造中必须保住** | ✓ |
| **美学与极简**（#8） | 一半面板过度解释（页脚三行图例）、另一半零解释（裸提示） | ✗ |

### 2.1 诺曼两个鸿沟

- **执行鸿沟**：屏上只有暗号，用户拼不出「我该按什么」。`缓存管理> `（`handlers_cache.py:289`）与 `选择 > `（`handlers_config.py:215`）是极端形态——连返回键都没说。
- **评估鸿沟**：按了不知道发生了什么。rf-730「游标只在临时反馈行」正是此鸿沟的实例；修复后由 `panel_runtime` 的 `repaint="feedback"` 承担，但**反馈文案**仍未契约化。

### 2.2 一致性实证：同一概念，处处不同

| 概念 | 面板 A | 面板 B | 面板 C |
|---|---|---|---|
| 怎么选 | 编号（`输入编号切换 (0-6)`，`handlers_config.py:753`） | 字母（`请选择 (A/D/R/0)`，`handlers_config.py:612`） | 键名 / 编号对（`输入两个编号交换优先级（如 3 1）`，`:961`） |
| 回车是什么 | 确认默认项（`回车=用缓存生成`） | **取消**（`直接回车取消`，`handlers_whatif.py:84`、`:102`） | 跳过（`:154`）/ 全部（`handlers_report.py:67`）/ 最新（`handlers_qa.py:125`） |
| 返回上层 | `0 返回` | 空回车返回（`default_key="0"`） | 编号范围里隐含（`(0-4)`，`:847`） |
| 提示完整度 | 教学式：`输入编号切换开关（如 3）· ?3 查看说明 · 0 返回`（`:556`） | 只列键：`(A/D/R/0)` | **完全没有**：`缓存管理> ` |

**回车一键五种含义**（确认默认 / 取消 / 跳过 / 全部 / 最新），其中「回车=取消」与「回车=确认」并存最伤：用户学到「回车=继续」后，在 What-if 文件选择里回车反而取消了操作。

### 2.3 两个硬伤

| 硬伤 | 事实 | 后果 |
|---|---|---|
| 编号断层 | 主菜单为 `1 / 2 / 4`，**没有 3**（`tui_menu.py` `MENU_ITEMS`） | 按 3 得到「未登记键」反馈；不是用户错，是界面在误导 |
| 帮助孤岛 | 7 处 `panel_loop` prompt 有 5 种写法定式，`?` 帮助仅 1 处 | 其余面板只能靠试错或翻手册 |

## 3. 根因分析

| # | 根因 | 说明 |
|---|---|---|
| R1 | **文案层无契约** | `DESIGN.md` 让 Web 的样式问题有唯一判据（配色/字阶/组件六态/空态文案 + 契约结构测试）；TUI 文案至今无判据，只能靠用户实测事后发现 |
| R2 | **演进方式是「加一把键 + 加一段确认」** | 每个需求新增直达键与确认屏，键位空间（19 项平铺）与提示串（5 种定式）同步膨胀，无人负责收敛 |
| R3 | **度量缺失** | 只有「问数」「通过/失败」，没有「击键数」「屏幕是否含语义」这类可机检的人因指标，于是优化总是被工程指标带跑（rf-728 即实例） |

## 4. 设计原则

| # | 原则 | 落地含义 |
|---|---|---|
| P1 | **识别优于回忆** | 编号是第一入口（数字对中文标签零助记成本），字母仅作别名 |
| P2 | **一键一义** | 同一按键在全应用只有一个含义；冲突时改语义，不改文案去圆 |
| P3 | **屏幕自解释** | 不翻手册即可完成主路径；帮助入口（`?`）在任何面板都可用 |
| P4 | **专家快路不牺牲可发现性** | 直达键/键名/组合输入保留，但必须出现在屏幕可发现的位置（页脚或 `?`） |
| P5 | **可机检优先** | 每条纪律都要有守护载体（结构测试/机检脚本/任务脚本），不靠口头纪律 |

## 5. 交互契约 v0（plan-156 的产出物雏形）

> 本节即未来 `DESIGN-TUI.md` 的骨架；最终形态由 plan-156 定稿并配结构测试（参照 `src/test/unit/report/test_design_doc.py` 的守卫方式）。

### 5.1 键分工总表

| 键 | 唯一语义 | 备注 |
|---|---|---|
| 数字 | **选择项**（第一入口） | 主菜单与各面板编号连续，无断层 |
| 回车 | **执行本行提示标注的默认项** | 默认项必须显式标注（见 5.3）；禁止用回车表达「取消」 |
| `?` | **帮助**（无参=本面板可用键一览；`?N`=第 N 项详情） | 全面板统一，由 `panel_runtime` 提供 |
| `0` | **返回上一层** | 全面板统一（已有达成，继续守住） |
| `Esc` | **取消当前提示 / 返回上一层** | 不得用于「退出程序」（退出走 `0`/`X`） |
| 字母 | **直达别名**（专家快路） | 必须出现在页脚或 `?` 帮助里，不得只存在于代码 |

### 5.2 提示行三段式模板

```
  [<动作指令>]（如 3）· [默认项声明] · ? 看说明 · 0 返回:
```

强制成分：

1. **动作 + 一个具体示例**（「输入编号切换开关（如 3）」优于「请输入编号」）；
2. **默认项声明**（回车会做什么）；
3. **帮助入口**与**返回键**；
4. 超长走 `wrap_prompt`/`wrap_hanging` 折行（已有窄屏机检）。

禁止形态：裸提示（无返回键说明）、只列按键字母（`(A/D/R/0)`）、只用占位符描述（`? 编号 看说明`）。

落地约束：模板化（plan-159）、回车语义（plan-157）、`?` 帮助（plan-158）三者共用本模板与同一批用例，须**同一 PR 交付**（见 7.2）。

### 5.3 默认项与取消的标注语法

| 场景 | 写法 | 禁止写法 |
|---|---|---|
| 回车执行默认 | `回车=用缓存生成`（默认项是**动作**时写明动作名，不只写「默认」） | `回车=确定`（无信息量） |
| 需要取消 | 用 `0`/`Esc`；确需回车取消时写 `回车=取消` 并**在句首**声明 | `（直接回车取消）` 藏括注里 |
| 二选一 | `(y/N)` 大写=N 为默认 | 大小写混用无默认暗示 |

### 5.4 术语对照表（内部词 → 用户词）

| 内部词（禁用上屏） | 用户词（上屏） |
|---|---|
| 强刷 / force | 重新生成（会调用 AI，计费） |
| 走缓存 / cache hit | 用已有结果（免费，可能不是最新） |
| 降级 | 改用备用方案（结果可能略旧） |
| 分档 / tier / 窄档宽档 | （不上屏；版面差异用户无需知道名字） |
| 游标 / cursor | 选中项 |
| 配置漂移 | 与出厂默认不同 |

### 5.5 反馈与空态口径

| 场景 | 口径 |
|---|---|
| 进行中 | `[..]` + 具体动作（「正在获取行情（3/12）」优于「处理中」） |
| 成功 | `[OK]` + 结果（含数量/路径/金额等可核对的量） |
| 部分失败 | `[!]` + 哪部分失败 + 影响 + 怎么办 |
| 错误 | `[ERR]` + 原因 + 下一步动作（不得只给异常类名） |
| 空态 | 说清「为什么没有」+「怎么才会有」 |

## 7. 实施顺序

### 7.1 波 0：判据先行（plan-156、plan-160、plan-165 的基线步）

先定契约与判据，再动机检。理由：没有判据就改动文案，等于把 14 轮个案修补再来一遍。本波不改变任何现有行为——只新增契约文档、结构测试、违例机检骨架，并**先行采集击键数基线**（`plan-165` 第一步）；`plan-160`（补 3 号键）体量极小，顺带交付。

### 7.2 波 1：提示层一次性收敛（plan-157 + plan-158 + plan-159，同一 PR）

三者改同一批 prompt、同一批用例、同一个 `panel_runtime`，分开做等于重复改同一处。交付后「像记密码」「猜哪个键」「不知道能否取消」三类体感问题一并消除，是本设计的主要收益来源。同批必跑 `dev-verify` + 面板窄/宽两档用例（C29 语义不变）。

### 7.3 波 2：摩擦清理（plan-161、plan-162）

`press_any_key()` 收敛与术语改写。放在波 1 之后的原因：术语对照需覆盖波 1 新产出的提示文案，先改会改两遍。

### 7.4 波 3：结构与防回退（plan-164 → plan-165）

主菜单按任务重组（生成 / 查看 / 配置 / 诊断）+ `/` 过滤，随后把击键数与屏幕语义固化进门禁，使后续新增面板无法回退。主菜单重编号会改变击键数基线，故排在基线之后、而非之前。

### 7.5 决策项（plan-163，可不交付）

Esc 复核的合法结果包含「实测无风险 → 维持现状」。判为不改动即按「已评估未采纳」归档关闭，不占交付窗口。

## 9. 风险与不做的事

| 项 | 处置 |
|---|---|
| 机检误报 | 存量挂账机制：首轮只报新增违反，存量按批次清零；词表/模板集中维护 |
| 面板批量迁移回归 | 每面板迁移必须保留窄/宽两档用例（C29 语义不变）；任务脚本兜底主路径 |
| 窄屏版面 | 提示变长会挤占窄屏（40 列基准），一律走 `wrap_prompt` 折行；模板必须自带折行 |
| 不引入富 TUI 框架 | 不引入 textual/rich 全屏，不改变现有逐行打印模型（与「管道/日志可读」兼容） |
| 不改窄屏分档语义 | 分档只改版式不改语义（C29），本设计不触碰分档边界 |
| 不重写 `panel_runtime` | 只在其上增加「提示生成」与「帮助」两处能力，保持既有 28 例语义 |
